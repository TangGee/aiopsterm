# Database Workspace

The Database workspace manages saved connections, schema browsing, table data, and SQL consoles through backend-owned runtimes.

- Database workspace labels follow the effective application language through explicit locale keys. Simplified Chinese (`zh-CN`) uses Chinese labels; locales without a database-specific translation use their existing base locale.
- Connection test, save, connect, disconnect, refresh, group, and delete actions use structured backend result envelopes. Renderer state should not mark a connection as ready unless the backend result is successful.
- New network connections receive an editable automatic name in `<database/service/catalog>@<host:port>` form. When no scope is configured, the engine name is used before `@`; changing connection fields keeps the automatic name in sync until the user edits Name directly. Duplicate automatic names receive `-2`, `-3`, and later suffixes.
- New SQLite connections use the selected file name, including `.db`, `.sqlite`, or `.sqlite3`, as the editable automatic connection name. Linux and Windows file paths follow the same rule.
- Database workspace state version 2 migrates version 1 connection names only when they exactly match an old system default such as `sqlite-connection` or `postgresql-connection`. Connection ids and credentials stay unchanged, migrated duplicates receive numeric suffixes, and explicit names in version 2 are preserved.
- A real SQLite file is queried through its `main` catalog. For the usual single-catalog SQLite connection, the sidebar hides the internal `main` row and renders `tables` directly below the connection, avoiding a repeated file-name level; table actions still send `main` to the backend. SQL and DB AI pickers, default SQL file names, export metadata, chart/comment scopes, and AI context summaries display the file name while query, mutation, and comment identity payloads retain `main`. Legacy or fallback SQLite catalogs are normalized to `main` before persistence.
- Clicking an expandable Database tree container row toggles it as well as selecting it. This applies to groups, connections, catalogs, schemas, schema object folders, and the flattened SQLite `tables` folder; their chevrons continue to toggle without changing selection. Table rows remain single-click select, double-click open, and chevron-only column expansion so the open gesture does not conflict with row expansion. Leaf rows only select.
- Presto scope controls are labeled **Catalog**, and Oracle scope controls are labeled **Service**. Presto discovers catalogs with `SHOW CATALOGS` without sending a configured catalog header. PostgreSQL/KingBase use `current_database()` when the saved Database field is empty, while Oracle and SQL Server prefer their server-reported Service/Database; these single-database scopes are written back after connect or refresh so later edits do not restore stale values.
- Default SQL and DB AI schema selection follows engine semantics: PostgreSQL/KingBase prefer the login-user schema and then `public`, Oracle prefers the login-user schema case-insensitively, SQL Server prefers `dbo`, and Presto prefers `default` before falling back to the first available schema.
- The SQL editor loads Monaco on demand when the SQL workspace is opened, instead of adding the editor runtime to app startup.
- **Run all** splits common SQL scripts at statement boundaries and executes each statement sequentially. Semicolons inside quoted values, quoted identifiers, comments, and PostgreSQL dollar-quoted bodies do not split a statement; an error result for one statement does not stop later statements. Each statement has its own result tab.
- Repeated SQL execution reuses completed, unpinned result tabs instead of growing the tab strip indefinitely. Pin a result tab to keep it for comparison; pinned and still-running results are never overwritten. Execution records remain in **Overview**, but when a result slot is reused, its older history record no longer reopens the replaced result data.
- Open table and SQL tabs, the active Database tab, loaded table data, and unsaved in-memory tab state remain available when switching to another top-level workspace and back. This cache is session-scoped; closing the application still starts a new Database tab session.
- When many Database tabs are open, the tab list scrolls horizontally while the New SQL (`+`), DB AI, and tab-list controls remain pinned and available at the right edge. The tab-list menu expands for longer titles within the viewport, truncates only titles beyond its maximum width with a full-name tooltip, and scrolls vertically when the list is taller than the available screen area.
- All SQL AI entry points share the persistent DB AI conversation pane; there is no separate visible AI drawer. **Explain** uses the selected SQL when available, otherwise the current statement, and returns conversational Markdown. **Optimize**, **Convert**, **Complete**, and natural-language-to-SQL requests appear as normal user/assistant turns with their SQL artifacts kept in the same history. AI requests opened from confirmed **DROP** or **TRUNCATE** table actions also enter this pane.
- The DB AI pane persists at most 24 individual message records for UI restore, but that UI cap is no longer the model-context limit. Each pane reset creates a new stable conversation id. The Cline session namespace combines that id with response language, connection, database, and schema, so switching any of those boundaries cannot reuse the old database transcript or system prompt. Existing visible history seeds each context-specific Cline session once, then Cline keeps canonical model/tool messages across turns and compacts context with its `basic` strategy when needed. The current database context and user prompt are added per turn; resetting the pane prevents an old persisted Cline conversation from being reused.
- DB AI snapshots its response language when a request starts. Requests created under Simplified Chinese use Chinese system and action prompts and require Simplified Chinese explanatory responses; requests created under every other locale use English prompts and require English responses. SQL, identifiers, code, original errors, and professional terms such as `table`, `column`, `index`, `constraint`, `schema`, and `database` remain unchanged.
- DB AI schema context comes from the current saved connection catalog rather than seed-table metadata. The Cline database profile exposes only `search_database_objects`, `describe_database_table`, `get_database_table_ddl`, and `query_database_table`; arbitrary SQL and writes are unavailable. The connection, database, and schema are bound by Electron main and cannot be replaced by model tool input. Selected or SQL-referenced objects may also be preloaded as bounded context. DDL lookup is best effort, so a permission failure falls back to catalog metadata instead of failing the AI request. MCP metadata, DDL, comments, identifiers, and rows remain delimited untrusted tool data rather than system instructions.
- External Agents can use the same read-only Database MCP tools through Export MCP after `Allow external Agents to read databases` is explicitly enabled. Arbitrary SQL and write operations are not exposed. Strict data queries require an engine that can hold a stable base-table identity; ClickHouse and Presto MCP data queries fail closed while their metadata/DDL tools remain available. See [Database MCP](../technical/database-mcp.md).
- Generated-SQL turns provide inline **Copy**, **Replace**, **Insert**, and **Run** actions. **Convert** also keeps its target-dialect selector with the result. **Run** accepts read-only SQL only and requires the current SQL tab to match the connection, database, and schema captured for the generated artifact; switching tabs cannot silently execute it against a different context. Active pane or structured-generation requests can be cancelled, and the conversation plus SQL-action metadata survive the existing DB AI persistence flow. Switching top-level workspaces does not cancel an in-flight response; an application restart restores unfinished responses as cancelled, reset conversations ignore late responses, and backend/IPC failures finish as visible error turns instead of leaving the composer locked.
- DB AI pane state saves are serialized, pending first-open or context-change snapshots are flushed before a request is created, and automatic saves pause across the create/start handoff. Duplicate sends are ignored during that handoff, so an older renderer snapshot cannot replace the backend-created request.
- SQL execution-error diagnosis remains inline with the failed SQL result. It can still apply a diagnosed statement to the editor, but it does not open a second AI surface. The local UI retains the original driver error; the copy sent to a model provider is bounded and redacts saved connection, endpoint, login, proxy, credential-shaped, and IP details.
- Table-page and SQL-result exports send a detached snapshot of the visible columns and rows to the backend, so Vue reactive state is never passed across Electron IPC and nested JSON, dates, and binary values remain cloneable.
- SQLite user-data work runs in a worker thread so synchronous `better-sqlite3` operations do not block the Electron main process event loop. This includes connection tests, schema refreshes, table-page queries, DDL lookup, mutation planning, mutation transactions, and raw SQL execution.
- SQLite reader results are capped at 5000 rows. When more rows exist, the execute result sets `truncated: true`, the execution message reads `Execution OK (first N rows, result truncated)`, and the renderer result payload carries the `truncated` flag; treat the returned rows as a bounded preview and narrow the query or use an export/offload path for full result sets.
- SQLite write statements return the changed row count and still record execution metadata in the shared SQL execution history shape.

Large Database result sets should stay bounded at the backend contract. Do not raise renderer payload limits to browse full tables; use paged table views, filters, or explicit export flows.
