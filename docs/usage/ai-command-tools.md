# AI Command Tools

Classic host-management AI runs on the official Cline SDK through an aiopsterm sidecar. The three profiles expose different capabilities:

| Mode | Cline tools | Behavior |
| --- | --- | --- |
| Chat | None | Explains and advises without claiming to operate a terminal. |
| Command | `propose_host_command` | Produces one command proposal for operator review and never executes it. |
| Agent | `run_host_command` | Runs a tool loop against the terminal session selected before the turn. |

Cline's local shell, filesystem, browser, MCP-settings, subagent, and team tools are disabled. The model cannot select a host, IP address, username, credential, or terminal session through tool arguments. Electron main binds the task to the selected live terminal session and maps Command proposals or Agent approval requests into the existing structured command-card contract.

The AI panel renders that backend-owned message only as a command card, not as duplicate free-form text. The card has a `Command` header, target host metadata when available, line count, copy action, executable command text, a large review dialog, and Reject / Execute controls. Command-mode proposals remain editable before execution: saving updates the structured command data and conversation snapshot, and Save and Run uses the normal terminal path. An Agent-mode command waiting on Cline approval is immutable because main will execute only the exact command and `toolCallId` that it approved; its dialog can be reviewed or copied but cannot replace the pending command. Failed, already-sent, or rejected non-pending command cards can be edited again, while running commands remain locked. Read-only diagnostic commands may show `查询类自动执行`; redirection, subshells, command substitution, multiline/interpreter wrappers, interactive/follow commands, destructive operations, and uncertain commands stay approval-gated. Copy uses the structured command text instead of the whole assistant message. Execute requires an active backend terminal session; without one, aiopsterm shows the terminal-unavailable notice and never reports a fake result. Reject persists `action: "rejected"` and disables terminal actions until an editable proposal is reopened and saved.

In Agent mode, Cline owns the model -> tool -> result -> model loop. Electron main independently applies the terminal security policy. A blocked command is rejected; a command requiring operator confirmation becomes a command card whose Approve/Reject action resolves Cline's pending approval Promise. A strictly classified low-risk read-only command may auto-continue only when Auto Approval is enabled. Main records an execution proof for both automatic and manual decisions, deduplicates repeated callbacks, caps returned output at 256 KiB, and interrupts an in-flight terminal command when the turn is stopped. The renderer does not execute the command or start a second provider request. Tool-result, later approval, final-answer, cancellation, and error events are correlated by task, turn, tool call, terminal session, and renderer owner.

The composer keeps its Stop action available while a Cline task is starting, waiting for approval, or running a host command, even when the command card itself is no longer rendered as a streaming text message. Stopping rejects any pending approval, aborts the provider request, cancels terminal output capture, and sends an interrupt to the bound terminal session before the turn is marked cancelled.

Classic conversations are created before the first send. Existing transcript messages seed a new Cline session once; later turns reuse Cline's persisted canonical messages and built-in context compaction instead of resending a fixed last-message window. Historical command cards seed as completed history and are never replayed.

Assistant transcript text renders as sanitized Markdown. Fenced code blocks are shown as compact code cards with language, line count, horizontal scrolling, and copy controls instead of raw backticks. Structured `say: "command_output"` rows use a dedicated `OUTPUT` block with the original backend-owned terminal/MCP output and a separate copy action, so command results stay visually distinct from ordinary explanations.

The right AI sidebar starts as a real empty chat surface, not with client-fabricated assistant messages or sample workflow cards. New chat conversations persist and restore with an empty message list until the user sends a request. Legacy persisted welcome assistant prompts are stripped by the chat-history backend during non-seed startup, including old welcome rows embedded in otherwise real saved conversations.

The right AI sidebar keeps an open conversation tab strip inside the top AI header. The tab strip is the set of currently opened AI conversations, not the full history list: the active backend-selected conversation is opened automatically, New Chat keeps the previous tab visible while adding the backend-created empty conversation, and restoring a conversation from History opens it as another tab. Tabs shrink and scroll inside the header, while the right side keeps only New Chat and More visible. While a response is streaming, a command is running, or approval is pending, creating/restoring/deleting conversations and closing or switching away from the active tab are blocked with a notice; stop or finish the turn first. This keeps task events and the final response attached to their originating conversation. Closing an idle tab only removes it from the visible strip and switches to the nearest open conversation; it does not delete persisted history. Deleting history remains a separate backend action.

The AI input context row starts empty. The backend may expose suggested/default contexts in the catalog, but the renderer does not auto-select those hosts during startup or panel mount; users add contexts explicitly through `@ 添加上下文`, and every selected context chip has a remove control.

Sent user messages are read-only in the transcript. They can be copied, but clicking them no longer reopens an editable composer or mutates previous user turns.

The AI sidebar has no user-facing task or task-progress concept in Agent or Command mode. Agent responses appear in the chat transcript, and Command execution state is tracked on the generated Command card through rejected, pending, sent, or failed status. Internal request lifecycle rows are not rendered as a right-panel module. Model, context, history, export, and input controls remain functional from the initial empty state.

Provider settings are mapped into the Cline session. OpenAI chat-completions uses Cline's `openai-compatible` provider and OpenAI Responses uses `openai-native`. Base URLs that already include a version segment such as `/v1` or `/v3` are preserved. Add `#` at the end only when the provider root must not receive aiopsterm's automatic `/v1` suffix; the marker is stripped before the configuration reaches Cline.

Command execution still follows the terminal security policy from Settings -> Host Agent -> Conversation & Hosts -> Security Configuration. Commands blocked by policy stay blocked, commands requiring confirmation show the approval bar, and successful writes are accepted only after the terminal bridge confirms the exact backend session and byte count. Terminal output is rendered only from backend `terminal:data` events.

Chat history and Markdown export preserve `commandExecution` and command-card execution status, so restored or exported conversations keep the original command-tool metadata and the latest visible command-card result.
