# AI Command Tools

Classic host-management AI runs on the official Cline SDK through an aiopsterm sidecar. The three profiles expose different capabilities:

| Mode | Cline tools | Behavior |
| --- | --- | --- |
| Chat | None | Explains and advises without claiming to operate a terminal. |
| Command | `propose_host_command` | Produces one command proposal for operator review and never executes it. |
| Agent | Controlled analysis tools and `run_host_command` | Searches trusted app data, maintains a per-session plan, inspects selected hosts read-only, and runs approved commands. |

Cline's local shell, filesystem, browser, MCP-settings, subagent, and team tools are disabled. The renderer resolves up to five explicit `@host` references into a per-turn allowlist. The model may choose only a `targetId` from that list; it cannot provide an arbitrary IP address, username, credential, or terminal session. Electron main validates the target again and maps Command proposals or Agent approval requests into the existing structured command-card contract. With no selected host, Classic remains available for Q&A but exposes an empty host target list.

Only Agent mode exposes the controlled analysis tools. `search_knowledge_base` returns at most ten bounded snippets from aiopsterm's local knowledge index. `todo_read` and `todo_write` maintain at most 32 plan items in the current Cline session; this is application state and cannot select or modify another conversation. `access_mcp_resource` can read only an exact resource URI already listed on an enabled MCP server, and every read requires an explicit click on its resource approval card. Agent receives a bounded catalog containing only those resource names, URIs, and descriptions; MCP transport commands, environment variables, headers, and credentials are never included. Arbitrary MCP tool calls remain unavailable because resource approval does not authorize server-specific side effects.

When one or more hosts are selected, Agent also receives `read_host_file` and `search_host_files`. Both require one exact `targetId`, use Main's frozen terminal mapping, reject connection/session/credential fields, and run only fixed bounded read templates through the terminal bridge. Each request shows a target-bound read card and requires explicit approval; `查询类自动执行`, Auto Approval, and the MCP tool auto-approve setting do not bypass it. A file read is limited to 500 lines and 64 KiB per result. Search supports either filename globs or file-content patterns, with bounded result counts and a 64 KiB result cap. Paths, patterns, ranges, booleans, and glob filters are revalidated in Main even though the tool schema already constrains them. Host labels, file contents, knowledge snippets, and MCP contents remain untrusted evidence and cannot change approval policy.

Sensitive read cards belong to the current Cline task. Approval is accepted only while the exact task, turn, tool call, tool name, input fingerprint, renderer owner, and target or resource binding remain pending. A stale card, changed target, disabled resource, changed URI, restored pending card, or stopped turn is rejected without reading. Multiple model tool calls are still allowed, but Cline presents and executes them in order: one card is resolved and its result is recorded before the next approval appears. Rejecting or stopping a card produces a matching tool result so the model loop remains protocol-complete.

Large `run_host_command` results use an opaque session-bound `fileRef` instead of exposing a filesystem path. `read_host_command_output` reads a bounded chunk from that reference and rejects references from every other Cline session. It does not accept a local path or terminal id.

The AI panel renders that backend-owned message only as a command card, not as duplicate free-form text. The card has a `Command` header, target host metadata when bound, line count, copy action, executable command text, a large review dialog, and Reject / Execute controls. Command-mode proposals remain editable before execution: saving updates the structured command data and conversation snapshot, and Save and Run preserves the proposal's target binding. A general proposal created with no selected host has no host badge and may be reviewed or copied, but it cannot run on the active terminal implicitly. An Agent-mode command waiting on Cline approval is immutable because main will execute only the exact command, `targetId`, and `toolCallId` that it approved; its dialog can be reviewed or copied but cannot replace the pending command. Failed, already-sent, or rejected non-pending command cards can be edited again, while running commands remain locked. A command whose Agent tool call declares `requiresApproval: false` also shows `查询类自动执行` when Main security does not override that declaration; clicking it approves the current command and enables the same behavior for later turns in this Cline session. Copy uses the structured command text instead of the whole assistant message. Execute requires the card's bound backend terminal session; without it, aiopsterm shows the terminal-unavailable notice and never falls back to the active terminal or reports a fake result. Reject persists `action: "rejected"` and disables terminal actions until an editable proposal is reopened and saved.

In Agent mode, Cline owns the model -> tool -> result -> model loop. Every `run_host_command` call must include a boolean `requiresApproval` for the complete shell command. The model sets it to `false` for non-destructive diagnostics and to `true` for state changes, interactive or long-running work, and uncertainty. Electron main independently applies the terminal security policy and may always override the model toward approval or rejection. There is no second executable-name allowlist for automatic execution: when the model declares `false`, Main security allows the command, and Auto Approval, `自动执行只读命令`, or the current-session `查询类自动执行` switch is enabled, the call continues automatically. A missing or non-boolean declaration defaults to manual approval. Main records an execution proof for both automatic and manual decisions, deduplicates repeated callbacks, caps returned output at 256 KiB, and interrupts an in-flight terminal command when the turn is stopped. The renderer does not execute the command or start a second provider request. Tool-result, later approval, final-answer, cancellation, and error events are correlated by task, turn, tool call, terminal session, and renderer owner.

The composer keeps its Stop action available while a Cline task is starting, waiting for approval, or running a host command, even when the command card itself is no longer rendered as a streaming text message. Stopping rejects any pending approval, aborts the provider request, cancels terminal output capture, and sends an interrupt to the bound terminal session before the turn is marked cancelled. The UI can acknowledge the stop immediately, while another send in the same conversation waits for the old native turn to release; sends in other conversations remain available. Commands sharing one terminal run FIFO. After `Ctrl-C`, the next command waits for the old command's end marker or a trusted shell prompt, and an unconfirmed boundary isolates that terminal command channel instead of mixing output between tool calls.

Classic conversations are created before the first send. Existing transcript messages seed an absent or empty Cline session once; later turns reuse Cline's persisted canonical messages and built-in context compaction instead of resending a fixed last-message window. A Cline session-index or message-read error stops the turn instead of replacing native state with the UI projection. Historical command cards seed as completed history and are never replayed. Chat, Command, and Agent use the Product Session `conversationId` directly as their shared Cline scope while the profile, locale, selected hosts, and tool schema may change between turns; tool calls and results retain their explicit target identity in the transcript.

Assistant transcript text renders as sanitized Markdown. Fenced code blocks are shown as compact code cards with language, line count, horizontal scrolling, and copy controls instead of raw backticks. Structured `say: "command_output"` rows use a dedicated `OUTPUT` block with the original backend-owned terminal/MCP output and a separate copy action, so command results stay visually distinct from ordinary explanations.

The right AI sidebar starts as a real empty chat surface, not with client-fabricated assistant messages or sample workflow cards. New chat conversations persist and restore with an empty message list until the user sends a request. Legacy persisted welcome assistant prompts are stripped by the chat-history backend during non-seed startup, including old welcome rows embedded in otherwise real saved conversations.

The right AI sidebar keeps an open conversation tab strip inside the top AI header. The tab strip is the set of currently opened AI conversations, not the full session catalog: an active backend-selected conversation is opened only while its Product Session row is still open, and New Chat keeps the previous tab visible while adding the backend-created empty conversation. Tabs shrink and scroll inside the header, while the right side keeps only New Chat and More visible. Creating or switching conversations remains available while another conversation is streaming, running a command, or waiting for approval because task events and final responses are routed to their owning conversation. Closing or deleting the active running conversation first requests cancellation; ordinary switching leaves its turn running in the background. Closing any tab closes its Product Session row, stops that active Cline runtime, and removes it from the visible strip. The final Classic tab can also be closed: the selected conversation is persisted as empty, the message projection is cleared, and the existing empty chat surface remains available without creating a replacement conversation. Closing preserves the Classic projection and Cline transcript for later Agents restore; permanent deletion remains a separate action. New Chat creates the next conversation explicitly, and sending from the zero-tab surface creates exactly one conversation on demand before the turn. On first Classic entry and every return from Codex, the transcript opens at the latest message. Streaming text, appended tool cards, and late layout growth continue following the bottom until an explicit upward wheel, touch, scrollbar, or keyboard action cancels that intent.

The AI input context row starts empty. The backend may expose suggested/default contexts in the catalog, but the renderer does not auto-select those hosts during startup or panel mount; users add contexts explicitly through `@ 添加上下文`, and every selected context chip has a remove control. For a managed Classic `@host`, the primary label comes from the host's current name in Host Management. Its connection address remains visible as secondary information and participates in context search, so operators can find the same host by either its managed name or endpoint.

Selected knowledge documents, knowledge images, past Classic conversations, and uploaded text attachments are resolved by Electron main before the request reaches Cline. Automatic knowledge search sends only the bounded matched line ranges. Classic image input accepts JPEG, PNG, GIF, and WebP only. Each image may be at most 5 MiB, and one message may contain at most five images in total, including uploaded, pasted, and selected Knowledge images. The composer rejects an unsupported, oversized, malformed, or sixth image immediately and shows the reason; Electron main checks the media signature, actual decoded size, and combined count again before sending. A rejected image is never silently omitted from an otherwise successful prompt. Accepted images use the model provider's native image input rather than a filename placeholder. aiopsterm never treats a renderer path as permission to read an arbitrary local file. All referenced content is evidence for the current request and cannot issue commands or override Agent policy.

Enabled Settings -> Rules entries and migrated custom instructions apply to every Classic Cline profile. They guide response style and workflow, but cannot override the bound host list, terminal security policy, approval requirements, credential handling, or the requirement that execution claims be backed by a real tool result.

Sent user messages are read-only in the transcript. They can be copied, but clicking them no longer reopens an editable composer or mutates previous user turns.

The AI sidebar has no user-facing task or task-progress concept in Agent or Command mode. Agent responses appear in the chat transcript, and Command execution state is tracked on the generated Command card through rejected, pending, sent, or failed status. Internal request lifecycle rows are not rendered as a right-panel module. Model, context, history, export, and input controls remain functional from the initial empty state.

Provider settings are mapped into the Cline session. OpenAI chat-completions uses Cline's `openai-compatible` provider and OpenAI Responses uses `openai-native`. Base URLs that already include a version segment such as `/v1` or `/v3` are preserved. Add `#` at the end only when the provider root must not receive aiopsterm's automatic `/v1` suffix; the marker is stripped before the configuration reaches Cline.

Command execution still follows the terminal security policy from Settings -> Host Agent -> Conversation & Hosts -> Security Configuration. Commands blocked by policy stay blocked, commands requiring confirmation show the approval bar, and successful writes are accepted only after the terminal bridge confirms the exact backend session and byte count. Terminal output is rendered only from backend `terminal:data` events.

Chat history and Markdown export preserve `commandExecution` and command-card execution status, so restored or exported conversations keep the original command-tool metadata and the latest visible command-card result.
